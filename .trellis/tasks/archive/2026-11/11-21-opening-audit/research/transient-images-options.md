# 一小时临时图片与提示词历史：流程研究

只读依据：本地 `ac29727`，2026-11-21。未操作生产、删除数据或修改产品。用户已确认新生成图片/参考图保留一小时、长期保留提示词和参数、广场保留并允许用户主动上传；现有图片保留。正在发布的安全修复与此项分开。

## 结论

最小可靠路线是沿用异步任务与受管图片存储，新增**只作用于未来图片**的临时生命周期。浏览器通过本站短期图片地址接收结果，过期停止新的读取，现有清理器确认可删后回收实际字节。不能仅把上游 URL 返回给浏览器，也不能仅把现有保留天数改为一小时。

SQL、Worker 和旧永久引用如何兼容，统一见 [transient-worker-options.md](./transient-worker-options.md)。

### 现有规则的具体限制

- `prisma/migrations/20261115090000_image_retention/migration.sql:272` 保留天数最小为 1；`:439` 以图片创建时间减天数筛选。现有策略无法表达完成后 1 小时。
- `prisma/migrations/20261115180000_image_history/migration.sql:225` 将任务来源写成永久 `ImageHistoryReference` / `ImageReference`。`20261115090000_image_retention/migration.sql:99` 还直接查任务 `sourceImageUrls`、Canvas 场景/run 和投稿状态；因此只新增 `expiresAt`、清空展示 URL 或删一个引用表都不能正确处理。
- `20261112090000_image_storage/migration.sql:303` 禁止删除永久引用；旧根不能被删掉来实现新规则。必须在新生命周期中区分正在消费图片的任务与已完成的历史记录，保持旧数据原规则。
- `20261115180000_image_history/migration.sql:399` 的七天缓冲只针对 `CANVAS_IMPORT`，不是全部参考图或生成图。保存到 Canvas 的永久引用也与严格的一小时冲突，不能遗漏这一入口。
- 当前 `PENDING` 投稿也属于长期保护根（`20261112090000_image_storage/migration.sql:630`）；上传广场若沿用无限待审，会重新产生无法回收的占用。

## 临时交付、引用与界面

建议输出截止时间为任务成功完成后 1 小时，失败/取消沿现有准确补偿。参考图建议上传接纳后 1 小时停止用户读取及新任务复用；已经原子接纳的排队/执行任务保留内部消费权到终态，不能在 Worker 首次读取前删图。这个时钟选择应写入 PRD；不能从“保留一小时”推断为从提交按钮点击或页面关闭开始。

最少需要：

1. `ImageAsset` 新增明确的临时截止信息，例如可空 `expiresAt`（旧行保持 NULL），以及新任务/上传的生命周期归属；具体 SQL/Worker 协议由存储研究收口。不能只靠前端计时，或通过启用旧的全量清理顺便删除旧图。
2. 对未来临时图，当前使用中或交付结果不明的消费任务、读写租约仍保护实际字节，已确定结束的提示词历史不再永久占图。接纳图生图与到期清理在现有 reference epoch → 业务/额度/资产锁序下竞争：接纳先赢则保住这份已审核原字节；过期先赢则要求重传。不得先审核 URL 再让 Worker 从可替换的远端 URL 取另一份内容。
3. GET、HEAD、条件 304 和内部读取均需理解截止时间；公开读取到期即拒绝。正在读取、写入结果不明、复制未决仍按原安全规则等候，不能因为过期就减额度或 `rm` 路径。内部任务授权读取与用户重新复用应明确区分。
4. Canvas 旧资料继续保留；新临时图不能因保存场景/run 就悄悄变成永久图。若 Canvas 纳入新规则，新场景保留参数和占位，过期图须重传，不能绕过其既有七天/保存根协议。广场批准是明确的持久化例外，普通生成历史不是。

`GenerationJob` 已有 prompt、negativePrompt、model、size、quality、count、seed、状态和计费等（`prisma/schema.prisma:439`），无需另造“提示词历史”表，也不应删 job 触发作品/对话级联。小型资产清单、计费与审核记录仍需保留；“只留提示词”应解释为用户历史不长期保存图片字节，不能承诺数据库只剩一个文本字段。

界面可复用现有 `available/cleaned/unavailable`（`src/lib/storage/image-availability.ts:20`）和无图占位，增加截止时间及“请在一小时内下载”。历史继续展示参数、状态、扣费和重用按钮。终态轮询已停止（`src/components/create/hooks/use-image-poller.ts:136`），所以已打开页面还需按截止时间更新一次状态，并在恢复焦点时核对，不能等永久轮询。

参考图重试有一个必须联动的边界：`src/lib/storage/image-source-presentation.ts:29` 会过滤不可用来源，`src/components/create/generator-studio.tsx:1059` 只在剩余数组为空时拒绝。若四张中一张过期，不能静默带剩余三张重试。需返回整组可复用状态，或发现任何原始参考图失效就阻止原任务重试并要求重传；保留参数和原生成类型，不能自动变成文生图。

### 缓存必须一起处理

`src/lib/image-url.ts:45` 将生成图送到 `/_next/image`；本地已安装 Next 的 `node_modules/next/dist/shared/lib/image-config.js:108` 默认 `minimumCacheTTL=14400`（4 小时），`next.config.ts:23` 没有覆盖。源图路由 `src/app/media/images/[token]/route.ts:19` 还返回 `public,max-age=300`。仅删除源文件或隐藏 UI，优化缓存仍可能在一小时以后提供副本。

最小候选是给新临时图独立地址空间：直接由本站短期读取，前端不走 Next 优化，服务端同时拒绝手工构造的该类 `/_next/image` 请求；旧持久图/广场继续原优化。另一方案是在每次优化缓存命中前验证期限，但改动更广。只给 `<img>` 加“不优化”不足以堵住手工入口。新临时 URL 的旧永久路由别名也不得旁路截止。已经被浏览器下载或由用户保存的副本无法撤回，不作这种承诺。

## 广场上传的最小衔接

独立图库详细研究见 [transient-gallery-options.md](./transient-gallery-options.md)。

当前 `GenerationImage.jobId` 必填（`prisma/schema.prisma:548`），作品查询、署名权限和点赞均依赖真实生成任务；`src/app/api/me/works/[id]/showcase/route.ts:30` 只是提交现有作品，不是文件上传。

建议独立小型 `GalleryWork`，存 owner、受管 asset、可选提示词/参数快照、投稿/审核时间及状态、公开署名快照；复用现有作品展示 DTO、审核状态函数、分页/点赞语义。不要伪造成功的 GenerationJob，也不要仅为上传把真实生成的必填 job 关系放宽，影响 Worker 与不可变历史绑定。

新上传先鉴权/限额、校验真实格式与大小，按现有共享严格审核检查**实际要保存的原字节**、公开文字和昵称快照，再进入受管存储；审核故障不能保存为可公开作品。使用真实字节预留，并与生成共用 5GB。原图已生成不代表新上传可免审核，客户端不能指定别人的 asset、公开昵称或批准状态。

待审必须有明确到期时间，且待审图片只给本人和管理员读取。可沿用 1 小时作为最省规则的默认值；如果人工审核需要更久，应把待审时限作为独立明确的运营例外，不能无限期 PENDING。批准时以投稿版本、仍有效/未删除的 asset、未封禁作者为条件，在同一事务取消待审到期并建立持久 SHOWCASE 根；到期清理先赢就返回 409 要求重传，不能批准空壳或复活删除中的对象。撤回/拒绝/超时移除可变保护并交给既有清理；旧管理员页面仍用 submittedAt 快照防撤回重投竞态。下架后的保存时长同样需要明确，不能借普通 PRIVATE 永久占用。

用户主动上传批准后才持久展示；旧广场作品与旧图保持。首次只做图片上传，不能把此需求默认为新增视频文件上传能力；旧视频展示规则保持。

## 新备份也必须排除临时字节

旧历史备份不删除、不改写。新模式上线后，未来发布备份/定时备份不能继续无差别打包图片卷，否则临时原图会在归档中长期存在；数据库备份保留提示词、参数、计费和必要资产清单即可，新任务不得退回把 base64/data URL 存进数据库。

最小候选是在受管存储里给未来临时对象固定独立前缀/目录，所有新备份明确排除该区；持久图库与旧图照常备份。若图库待审也放在临时区，批准必须通过既有受管复制/确认流程进入可备份的持久归属，不能仅清掉 expiresAt 却仍被备份排除。另一选择是从一致数据库快照生成“旧持久图 + 已批准作品”的精确对象清单，仅备份清单对象；不要凭文件扩展名、目录修改时间或未经确认的当前状态猜测。

临时图不要求恢复原字节。恢复数据库后，这些记录即使还有资产/对象元数据，UI 也应按截止/实际可读性显示已清理，不能宣称已恢复图片；不能因此误减不明对象的计账或运行无范围的删卷。客户端短期缓存、Next 优化缓存、运行日志/调试转储同样不应变成长期临时图备份。最小方案优先完全不备份临时字节，不再引入一套“备份也每小时删除”的调度。

## 5GB、异步任务与验证边界

`contracts/media/v1/contract.json:5` 同时限制实际占用和预留：每个输出先预留 50MiB，四张就是 200MiB。5,000,000,000 字节约容纳 95 个这样的最大输出槽，不是只能存几张；实际图片数量取决于文件大小。1 小时减少长期实际占用，**不会消除排队预留高峰**，每用户五张/分钟也不是全站容量上限。上传待审和已批准广场同样占用这 5GB，持久广场最终仍可能填满；应正确拒绝并显示额度，不自动加上限或挤掉旧图。

`src/app/api/generate/route.ts:417` 返回任务，浏览器随后轮询；`worker/internal/worker/generation.go:400` 接收上游 base64 或下载 URL，再由 `storage.go:109` 受管保存。Worker 与提交请求不共享一个持续的浏览器连接。完全不暂存而直接转发原字节，需要重新设计结果通道、断线/重启恢复和上游回执，并非本需求的最小修改。上游 URL 也可能短命或带签名，不能公开替代本站地址；更不能把 provider 凭据交给客户端。关闭受管存储退回 data URL/S3 不等于临时模式，反而可能把图片塞回长期数据库或绕开额度。

必要回归：59:59 与 60:00 的 GET/HEAD/304/手工优化请求；任务排队超过参考图对外期限后仍读取相同已审核字节；临界接纳与清理双连接竞争；任一参考图失效拒绝整组重试；终态历史保留所有参数；批准与到期同时发生、撤回重投后的旧审批；待审不可公开与无效格式/审核故障零上传；真实5GB used+reserved竞争；旧图/旧Canvas/旧广场及未决 I/O 不受新模式删除。需要追加迁移、Node/Go 同步契约及真实数据库测试，本报告没有运行这些未来功能测试。
